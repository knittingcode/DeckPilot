# Internationalization

DeckPilot's interface is translated into English and Polish. English is the source language and
the fallback. This page describes how translations are organized, how the language is chosen,
how to add strings or a language, and the checks that keep the translations complete.

## Architecture

The desktop app (`apps/desktop`) uses [i18next](https://www.i18next.com/) with `react-i18next`.

| Path                                         | Contents                                                                                        |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `src/i18n/config.ts`                         | Supported languages, namespaces, each language's own name                                       |
| `src/i18n/locales/<lng>/<ns>.json`           | The resources: one file per namespace and language                                              |
| `src/i18n/resources.ts`                      | Imports every resource file statically (no HTTP backend, nothing loaded at run time)            |
| `src/i18n/index.ts`                          | The i18next instance, `useTranslation`, `Trans`, `TranslationKey`, `applyLanguage`              |
| `src/i18n/i18next.d.ts`                      | Typed keys: `t("ns:key")` is checked against the English resources                              |
| `src/i18n/resolve.ts`                        | `resolveLocale(preferred, supported)`: the language for a list of preferred languages           |
| `src/i18n/system-locale.ts`                  | The operating system's preferred languages (Tauri command `system_locales`, else the webview's) |
| `src/i18n/preference.ts`                     | The stored preference: `system`, `en` or `pl`                                                   |
| `src/i18n/language.ts`                       | `initLanguage`, `setLanguagePreference`, `startLanguageSync`, `useLanguagePreference`           |
| `src/i18n/format.ts`                         | `Intl` formatters and `useFormat()`                                                             |
| `src/settings/pages/language.tsx`            | Settings → General → Language                                                                   |
| `src-tauri/src/commands/locale.rs`           | `system_locales()`: the system's languages as BCP 47 tags                                       |
| `scripts/i18n-check.mjs`                     | The consistency check (`pnpm --filter @deckpilot/desktop i18n:check`)                           |
| `scripts/i18n-dynamic-keys.json`             | Patterns of keys built at run time (empty today)                                                |

The instance is initialised synchronously in English when `src/i18n/index.ts` is first imported,
so every component and every test can translate without a provider or setup file. `main.tsx`
then resolves the user's language and switches to it before the window's first render.

Namespaces: `common`, `navigation`, `settings`, `devices`, `layouts`, `editor`, `actions`,
`workflows`, `workspace`, `marketplace`, `plugins`, `permissions`, `dialogs`, `security`,
`notifications`, `errors`. The default namespace (for keys without a prefix) is `common`, but
keys are always written with their namespace: `t("security:locked.title")`.

## Language detection

With the preference `system` (the default), the language follows the operating system's list of
preferred languages, in its order:

| Platform | Source (through the `sys-locale` crate)                                              |
| -------- | ------------------------------------------------------------------------------------ |
| macOS    | The preferred-languages list (System Settings → General → Language & Region)         |
| Windows  | The user's preferred UI languages (`GetUserPreferredUILanguages`)                    |
| Linux    | `LANGUAGE` (a colon-separated list), then `LC_ALL`, `LC_MESSAGES`, `LANG`            |
| Browser  | `navigator.languages` (development in a plain browser, and the tests)                |

`system_locales` turns POSIX names into BCP 47 tags (`pl_PL.UTF-8` → `pl-PL`), drops `C` and
`POSIX`, and removes duplicates. `resolveLocale` then walks the list in order: an exact match of a
supported tag, else a supported tag for the language alone (`pl-PL` → `pl`), else the next
preferred language. When none matches, the result is English. So `de-DE, pl-PL` gives Polish
and `de-DE` alone gives English. The IP address, time zone or region are never used.

## The language preference

The preference is application-wide: it applies to every window and every profile on this
computer. Values: `system` (the default and the recommended choice), `pl`, `en`.

It is stored in the webview's `localStorage` under `deckpilot.language` (`system` is stored as
no entry). All windows of the app share that storage. It is deliberately **not** in the encrypted
configuration database: the unlock window must show the right language before the database is
open, and the language is a property of the computer, not of a profile. It is also not exported
with the configuration.

Earlier versions of DeckPilot had no language setting (the interface was English only) and stored
no language anywhere, so there is no earlier preference to migrate.

## Switching the language

Settings → General → Language changes the language at once, without a restart:

1. The preference is stored and announced to the other windows with the `deckpilot://language`
   event (`src/lib/window-sync.ts`).
2. Every window calls `i18n.changeLanguage` and sets `<html lang>`.
3. Components that use `useTranslation` re-render in the new language. Nothing is remounted
   (no provider gets a new `key`), so unsaved edits, selections, open dialogs and the text in form
   fields stay as they are.

When a window gains the focus it reads the stored preference again (in case it missed an
announcement) and, with `system`, asks for the system's languages again, so a change the
operating system reports to running apps shows the next time the user returns to DeckPilot (see
[Platform limitations](#platform-limitations)).

Texts that were already produced in the previous language stay in it: notifications in the
notification center and toasts are created in the language of the moment they happen.

## Fallback rules

- A language that is not supported (`de`) shows English.
- A regional tag shows its language (`pl-PL` → `pl`; `load: "languageOnly"`).
- A key missing in Polish shows the English text. The CI check prevents this for first-party
  strings; it can only happen with a resource that was changed by hand without the check.
- Data the user or a plugin provides (profile, layout, action and device names, module names from
  their manifests) is shown as it is and never translated by the app; a plugin may ship its own
  translations ([Plugin localization](#plugin-localization)).
- A backend error is translated by its code; without a translation its English message is shown
  ([Backend errors](#backend-errors)).

## Resource format

Resources are i18next JSON v4, nested objects of strings:

```json
{
  "locked": {
    "title": "DeckPilot is locked",
    "resumes": "Your Stream Deck resumes as soon as it is unlocked."
  },
  "password": {
    "tooShort_one": "Use at least {{count}} character.",
    "tooShort_other": "Use at least {{count}} characters."
  }
}
```

- Keys are stable, dotted identifiers (`locked.title`), never the English sentence.
- Placeholders are `{{name}}`. Values are not HTML-escaped by i18next (React escapes them).
- Plurals use the `Intl.PluralRules` categories as suffixes. English needs `_one` and `_other`;
  Polish needs `_one`, `_few`, `_many` and `_other` (`1 projekt`, `2 projekty`, `5 projektów`,
  `22 projekty`; `_other` is used for fractions). Call `t("ns:key", { count })`.
- Markup inside a sentence uses numbered or named tags for `Trans`: `"Restore <file>{{file}}</file>
to the data folder"`.
- Never name a `Trans` tag like an HTML void element (`<link>`, `<br>`, `<img>`, `<input>`,
  `<hr>`, `<meta>`, …): `Trans` renders such a tag without its content, so the words inside it
  disappear. Use a name of your own, e.g. `<page>Open the page</page>`.

## Writing translatable code

- Import `useTranslation` and `Trans` from `@/i18n`, never from `react-i18next` directly (the
  import guarantees the instance exists).
- Move every user-facing string behind a key: text, `aria-label`, `title`, tooltips,
  placeholders, toasts and notifications.
- Never build a sentence from translated fragments (`t("a") + name + t("b")`) or from English
  conditionals (`"device" + (n === 1 ? "" : "s")`): give each variant its own key, use
  placeholders and plurals, and `Trans` for sentences that contain elements.
- Keys kept in data (a registry, a map from a state to its label) are typed `TranslationKey`
  and resolved with `t` when rendered. Prefer a literal map (`{ info: "notifications:severity.info" }`)
  over a key built from a template string, so the check finds every key.
- Helpers outside components may use `i18n.t`; the components that render their result must use
  `useTranslation` so they re-render when the language changes.

## Backend errors

Every Tauri command rejects with a `CommandError` (`src-tauri/src/error.rs`), serialized as

```json
{ "code": "invalid.layoutUsedElsewhere", "message": "the layout is also used by “Home”; …", "params": { "profiles": "“Home”" } }
```

- `code` is stable and derived in Rust from the variant and the kind of the inner error, never
  from its text. `params` (omitted when empty) are strings or numbers; a count is `count`, so
  plural keys work.
- `message` is the English text: for logs, for code that matches English (older agents), and as
  the fallback.
- `errorMessage(error)` (`src/lib/backend-error.ts`, re-exported by `@/lib/api`) returns
  `t("errors:<code>", params)` when that key is a text in the window's language, otherwise
  `message`; never a raw key. It still accepts plain strings (older builds, tests) and `Error`s.
  `failureMessage` and `toastFailure` use it. Match on `errorCode(error)`, with
  `rawErrorMessage(error)` only as a fallback for plain strings (`isAuthenticationRequired`,
  `credentialFailure`, `isNotSupported`).

Code families (the translations live in `errors.json`; the groups are in
`scripts/i18n-dynamic-keys.json`, since the keys come from the backend):

| Code | Source |
| --- | --- |
| `locked`, `confirmationRequired`, `authenticationRequired` | The variants of the same name. |
| `invalid.<reason>` | `CommandError::invalid(reason, message)` / `invalid_with(…, params)`: a refusal the user sees, e.g. `invalid.passwordIncorrect`, `invalid.workflowsRunning` (`count`). |
| `invalid` | `CommandError::Invalid(String)`: a rare or internal message; never translated, the message is shown. |
| `notFound.<thing>` | `CommandError::NotFound("device model")` → `notFound.deviceModel`. |
| `storage.<variant>` | `StorageError`, e.g. `storage.invalidKey`, `storage.crypto.passwordTooShort`, `storage.credentialsRequired.systemKey`. |
| `registry.*`, `engine.*`, `module.*`, `catalog.*`, `profile.*`, `projectContext.*` | The core errors of the same name, by variant (`profile.notFound.<thing>`). |
| `agent.notRunning`, `agent.closed`, `agent.io`, `agent.protocol`, `agent.tooOld` | `deckpilot_ipc::ClientError`. |
| `agent.<ErrorCode>` | An error the agent answered with (`IpcError`): `agent.locked`, `agent.failed`, …, with `reason` as a param when the agent gave one. Except `agent.locked`, the agent's message is the text. |
| `identifier`, `updater` | Message only. |

Codes whose text is only a detail (`invalid`, `storage.vault`, `storage.invalid`,
`storage.keyStore`, `storage.variable`, `registry.invalidPresentation`, `module.variables`,
`profile.invalidIcon`, `agent.failed` and the other agent answers) have no translation on purpose.
Plugin refusals of the marketplace commands keep their own `{ reason, message }`
(`src/plugins/api.ts`). The codes of failed plugin actions (`not-permitted`, `throttled`,
`bad-request`, …) are explained with `errors:pluginAction.<code>` when the plugin gave no message.

To add a code: return `CommandError::invalid("myReason", "english text")` (or a new variant
mapping), add `invalid.myReason` to both `errors.json` files with the same placeholders, and test
the payload in `error.rs`.

## Formatting dates, numbers and lists

`useFormat()` returns formatters bound to the language on screen: `date`, `time`, `dateTime`,
`number`, `percent`, `fileSize` (binary units with the language's number format, e.g.
`1,5 MB`), `relativeTime` (`Intl.RelativeTimeFormat`), `list` (`Intl.ListFormat`: `Praca, Dom
i Gry`) and `compare` (an `Intl.Collator`, for sorting by the language's alphabet). The plain
functions in `src/i18n/format.ts` take the locale explicitly. `formatTimestamp` in
`src/lib/format.ts` uses the window's language too.

## Adding a language

1. Add its code to `SUPPORTED_LANGUAGES` and its own name to `LANGUAGE_NAMES`
   (`src/i18n/config.ts`).
2. Copy `src/i18n/locales/en` to `src/i18n/locales/<code>` and translate every file.
3. Import the files in `src/i18n/resources.ts`.
4. Add the language's plural categories to `PLURAL_FORMS` in `scripts/i18n-check.mjs`
   (`new Intl.PluralRules("<code>").resolvedOptions().pluralCategories`).
5. Run `pnpm --filter @deckpilot/desktop i18n:check` and the tests.

The Language page lists every supported language automatically.

## Tooling and CI policy

`pnpm --filter @deckpilot/desktop i18n:check` runs in the CI's Frontend job (step
"Translations") and fails on:

- malformed JSON, duplicate keys in an object (a duplicate-detecting reader, since `JSON.parse`
  keeps the last), values that are not strings;
- namespace files that are not in `NAMESPACES`, or namespaces without a file;
- keys present in one language and missing in another;
- placeholders or `Trans` tags that differ between languages;
- plural forms that are not exactly the language's set;
- `t("ns:key")` or `i18nKey="ns:key"` in the sources with an unknown namespace or key;
- keys no source mentions (unused), unless they match a pattern in
  `scripts/i18n-dynamic-keys.json`.

**Policy:** every first-party key must exist in English and Polish before a change is merged.
A pull request that adds or changes a string adds or updates the Polish text in the same change.
Write Polish in the neutral register of the macOS Polish interface ("Zapisz", "Anuluj", "Wprowadź
hasło, aby odblokować DeckPilot.").

## Platform limitations

Choosing a language in Settings always applies at once, on every platform. Following a change
of the **system** language depends on what the operating system tells a running app:

- **Windows:** the user's UI languages are read live; a change shows when a DeckPilot window
  gains the focus.
- **macOS:** the system gives an app its language order when the app starts (System Settings
  asks to restart apps after a change), so a new order applies at the next start of DeckPilot.
- **Linux:** the locale variables of a running process do not change, so a new system language
  applies at the next start of DeckPilot.
- Native menus and dialogs drawn by the operating system (file pickers, Touch ID and
  credential-store prompts) follow the system's language, not DeckPilot's. The tray menu follows
  the app's language once the app has told the agent ([The agent's texts](#the-agents-texts)).
- Names of the credential store (`macOS Keychain`, …), and the details inside backend errors
  (SQL and file system errors, agent messages, plugin texts), are reported by the desktop process
  in English and shown as they are ([Backend errors](#backend-errors)).

## Coverage of phase 1

Translated: the app shell (toolbar with the device, profile and layout selectors, rail, status
bar and its items, notifications), the dialog system (modal shell, templates, dialog service,
credential dialog, password fields, credential failure messages), the security gate and the
native security windows (setup, migrate, unlock, confirm, authentication of sensitive
operations), and the settings shell (categories, page titles and descriptions, search, the
Language page). The settings pages' contents, the editors, the libraries, workflows, the
marketplace and module pages are still English and follow in later phases; the `editor`,
`actions`, `workflows`, `marketplace`, `plugins` and `permissions` namespaces exist (empty) for
them.

## The agent's texts

The background agent draws a few texts itself: on keys (*Back*, *Folder*, *Workflow*, *Missing*,
*Unavailable*, *Not in this profile*, *Error*, *No profile*, *No layout*, *No previous layout*, and
the default names of the `deck` module's actions such as *Next page* or *Switch layout*) and in the
tray menu. They come from a small catalog in Rust with stable keys (`deckpilot_core::i18n`:
`face.back`, `tray.quit`…), in English and Polish; the agent has no React and no i18next.

The app tells the agent its effective language (IPC protocol 13, `setLocale`) when it connects and
whenever it changes (`src/plugins/agent-locale.ts` → the Tauri command `set_agent_locale` → the
bridge in `src-tauri/src/agent.rs`, which sends it again to every agent it connects to). Only the
language tag crosses. The agent then:

- redraws only the keys whose title or detail comes from the catalog or is an action's default
  name; a title the user wrote (also one that reads "Back") is never touched, and nothing else is
  redrawn (the renderer handles Polish diacritics and every text mode of
  [key-text.md](key-text.md));
- rebuilds the tray menu in that language;
- shows plugin texts in it ([Plugin localization](#plugin-localization));
- reports it in `getStatus` (`locale`).

An agent of protocol 12 or older is not told and stays English; until an app says, every agent is
English.

## Plugin localization

Plugins (plugin API 1.6) ship their translations as `locales/<tag>.json` in their signed package
and name keys in their manifest texts as `"t:key.path"`; see
[docs/marketplace/sdk/localization.md](marketplace/sdk/localization.md) for the format, the
limits and the SDK (`ctx.locale()`, `ctx.t("key", &[("count", 3)])`).

- **Where they are verified.** A locale file is a file the manifest names: it is packed and hashed
  with the package, pinned by the registry (or by the bundled pins of a first-party plugin),
  checked when the package is installed (`deckpilot-plugin-package`: valid JSON, strings only,
  sizes, no markup) and again whenever the agent reads it (its digest against the integrity
  record). A changed file is refused; translations are never downloaded at run time.
- **Which language.** The app's effective language (`setLocale`), then its language without the
  region, the plugin's `defaultLocale`, `en`, and finally the manifest's plain text or a label made
  from the key. A missing key is logged once per plugin and key at debug level.
- **Where they show.** The installed plugin's name, description, actions (also in the Action
  Library), settings, credentials, permissions and their justifications, error messages and
  toolbar entries; its dialogs; keys titled with an action's default name. The app reloads them on
  the `changed` plugin events the agent sends after a change of language. The registry's own
  listing texts (summaries of plugins that are not installed) are the registry's and are not
  translated.
- **Isolation.** A plugin resolves only its own keys: it cannot read or override DeckPilot's
  translations or another plugin's. Plugin texts are plain text everywhere.
- **Lifecycle.** Catalogs are cached per plugin, version and manifest; an update or rollback reads
  the new version's files, uninstalling drops them.
